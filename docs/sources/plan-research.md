## 2. Hyphenate track document (read in full)

Source: "CalHacks_Hyphenate_Track" Google Doc (1u4iN8R97IL…), read Oct 24 via the mobile view. **VERIFIED.** The four judging questions and the "what to submit" list match the handoff exactly. Things the handoff does not have:

**Framing they want.** "Pick a company and one corner of its finance team: a few seats that work closely together… Then build the autonomous system you'd hire to fill them, and the company it works in: the software it uses, the people it answers to, and the mistakes hiding in its data." Be imaginative about the company, "strict about how it works underneath."

**"What makes it hard" (five named difficulties; the plan should show each one):**
1. **Sources that disagree.** "The bank, the ledger and the contract each tell a slightly different story. Acting well means knowing which one to trust, and saying why." For us: Jobber vs. QuickBooks vs. Gusto vs. a manager's text.
2. **Time.** "What happened in March should change what the system does in June." For us: cycle 2 behaves differently because of cycle 1's answers; backtests over past cycles.
3. **Working with others.** "Approvers are busy, colleagues… hand work over half done, and the controller sometimes says no. The system has to ask at the right moment and handle the answer." For us: reminders, partial replies, the owner rejecting a proposed rule.
4. **Limits.** "No company gives one employee access to everything… Whoever requests a payment can't be the one who approves it." For us: read-only sources, draft-only Gusto, the agent never approves its own correction.
5. **Explainable and accountable.** "Every call should trace back to the data, rule or person behind it, no matter how long ago it was made." For us: every flag links to the source record, the rule and the human answer that created the rule.

**Payroll is a listed sample workflow:** "Payroll. Payroll runs and stock grants turned into the right entries every period, by department and entity." So payroll is in scope for them, and the novelty has to come from the input-verification angle, not from "payroll" itself (matches the validation findings).

**Proof they accept:** "a test set, planted errors with an answer key, or a benchmark score." Our plan uses the first two.

**"People. A model can play the approver, the colleague or the auditor."** Useful for the judges' own scenario: a scripted "manager" persona can answer texts live when no real manager is available, as long as it is labelled simulated.

**Sandboxes and references they list** (none required): Stripe, Increase, Lago, Odoo, ERPNext; ledgers Formance, Blnk, TigerBeetle, Beancount/Fava; mocks Mockoon, Prism, stripe-mock; data SEC EDGAR; benchmarks AccountingBench, APEX-Accounting, Finance Agent Benchmark, DABstep, BenchRec, Invoice Sandbox Benchmark. "Models and frameworks. Use whatever you like."

**Key concepts they define** (use their words in the UI and pitch): system of record, reconciliation, materiality, internal controls, **segregation of duties** ("No single person, or system, can both start and approve the same action"), **audit trail** ("who did what, when and why"), controller.

Recommendation: **own table + embeddings in the main database** (Convex vector index if Convex is the backend; pgvector if Postgres), with Backboard as an optional mirror (`add_memory` for each confirmed lesson, `memory: "Auto"` for the owner's chat) only if the MLH Backboard prize is wanted and costs under an hour. Zep is the best hosted alternative if the team prefers not to write the classifier.
